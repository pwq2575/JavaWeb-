## 2. 测试策略 (Test Strategy)

### 2.1 测试分层金字塔

| 层级 | 范围与目标 | 工具与技术 | 规模 | 执行时机 | 责任 |
|---|---|---|---|---|---|
| L1 单元测试 | service 层纯业务规则：借期计算、续借上限、转交状态机、信誉判定与去重、投票可见性、防重逻辑；mapper 不测（薄） | JUnit 5 + Mockito，Mock `mapper` 与 `Clock` | 约 30 个方法 | 每次 `mvn test`，提交前 | 开发主写，测试补边界 |
| L2 接口测试 | Controller 契约：状态码 + 业务码 + 响应结构 + 参数校验 + 权限拦截；不经真实 UI | MockMvc + `@SpringBootTest` + `@AutoConfigureMockMvc` + `@WithMockUser` 或真实 JWT | 92 条用例中的自动化部分（85 条） | 每次构建 | 测试 |
| L3 集成测试 | 真实 MySQL 8 的约束行为：唯一索引 `uk_reservation_slot`、`uk_transfer_pending`、`uk_credit_daily`、生成列、CHECK 约束、事务回滚 | Spring Boot Test + 真实 MySQL 8 库 `ers_test` + `@Sql` 重置 | 每模块 1–2 条 | 每日构建 / 提测 | 测试 |
| L4 端到端 | 浏览器内完整业务链路：登录→借→续借→转交→归还→看板刷新；导出文件可打开 | 手工走查（Chrome/Edge），按 §4 用例步骤执行 | 7 条手工用例 + §7.2 兼容性 6 项 + 演示脚本 | 提测后 / 验收前 | 测试 + 产品 |
| L5 验收 | PRD §9 课程要求逐条对照，答辩演示路径 | 手工 + 文档比对 | §8 对照表 10 条 | 验收 | 课程组 / 指导教师 |

**关键决策：L3 集成测试必须使用真实 MySQL 8，不使用 H2。** 原因：场地防重与转交唯一性依赖 `STORED` 生成列 + 唯一索引（`active_slot`、`pending_asset_id`），借还并发依赖条件更新；H2 对生成列语法与 `CHECK` 行为兼容不完整，用 H2 会得到「本地全绿、真库冲突」的假阳性。集成测试统一指向 `ers_test` 库，测试类上标注 `@Sql(scripts = {"classpath:db/schema.sql","classpath:db/data-test.sql"})`。

### 2.2 自动化与手工分工

| 工作 | 方式 | 理由 |
|---|---|---|
| 业务规则与状态机 | 自动化（JUnit 5） | 规则密集、回归频繁、断言确定 |
| 接口契约与错误码 | 自动化（MockMvc） | 53 个接口的 code/status 组合最易回归破坏 |
| 数据库唯一约束与并发 | 自动化（多线程 + 真实库） | 并发窗口极窄，手工无法稳定复现 |
| 权限矩阵（角色 × 接口 × 资源归属） | 自动化（参数化） | 组合多，适合数据驱动 |
| 页面交互、交互动效、错误 toast 文案 | 手工 | 依赖视觉与交互体验，无 UI 自动化投入 |
| XSS 实际渲染、导出文件打开效果 | 手工 | 需浏览器 DevTools 与 Excel 实际打开验证 |
| 兼容性与响应式断点 | 手工 | 需真实浏览器窗口缩放 |
| 定时任务（逾期/爽约/截止） | 自动化为主 + 手工确认 | 单测调用 job 方法并注入固定 `Clock`，避免等待真实时间 |

### 2.3 执行策略与准入准出

| 项 | 内容 |
|---|---|
| 准入条件 | 代码编译通过；`db/schema.sql` 可在空库执行成功；`/swagger-ui.html` 可打开；种子账号可登录 |
| 提测门槛 | 后端 `mvn test` 全绿；L2 冒烟 20 条（§6）全部通过后才接收提测 |
| 执行顺序 | 冒烟（§6）→ P0 全量 → P1 全量 → P2 抽样 → 边界清单（§5）→ 安全专项（§4.10） |
| 准出条件 | P0 用例通过率 100%；P1 通过率 ≥95% 且无 S1/S2 遗留；S3 遗留 ≤3 条且有明确规避方案；导出文件在 Excel 中可正常打开 |
| 阻断条件 | 任一 P0 用例失败且无规避方案；数据库脚本无法重灌；登录链路不可用 |
| 缺陷回归 | 修复后必须执行该用例 + §9.3 关联回归集 |

### 2.4 测试数据原则

1. **演示库与测试库分离**：`ers` 用于手工演示与验收，`ers_test` 用于自动化；破坏性用例（删除、扣分、并发占用）只在 `ers_test` 执行。
2. **时间可控**：所有依赖「今天」的规则（借期 3 天、逾期天数、可约 14 天、投票截止）必须通过注入 `Clock` 或改写 `due_date`/`deadline` 构造，禁止靠等待。
3. **每个用例自备前置**：用例失败后不依赖上一条用例的残留数据；需要特定状态时用 §3.4 的夹具 SQL 显式构造。
4. **不使用生产数据**：全部数据来自 `db/data.sql` 与夹具，账号密码为演示弱口令，仅限本机。

## 9. 缺陷管理与回归

### 9.1 缺陷等级定义

| 等级 | 名称 | 判定标准（满足其一） | 示例 | 处理时限 |
|---|---|---|---|---|
| S1 | 致命 | 主流程不可用；数据错乱或丢失；越权导致数据泄露；服务启动失败 | 无法登录；借出后 `due_date` 不正确；普通用户成功调用 `/api/admin/**` | 当日修复，阻断提测 |
| S2 | 严重 | 核心规则失效但有规避路径；关键状态机错误；并发防重失效 | 续借可到第 4 次；同一时段可被两人预约；信誉限制未生效 | 1 个工作日内 |
| S3 | 一般 | 非核心分支错误、校验缺失、错误码/文案不符契约、导出格式问题 | 删除有流转记录资产返回 500 而非 42200；导出列顺序与文档不符 | 本迭代内 |
